# Выпуск и обновления через GitHub Releases

Подготовлено первое обновление **0.1.1** из актуальной `main` после слияния PR №4. Версия увеличена командой `npm run bump -- patch`; новые переводы в этой подготовке не добавляются. Репозиторий публичный, стабильная 0.1.0 опубликована. Слияние PR обновления, создание тега и публикация 0.1.1 выполняются отдельно владельцем; в рамках подготовки они не выполняются. Базовый ручной прогон 0.1.0 подтверждён пользователем для Foundry 13 / PF1 11.11 / Babele 2.9.1; сетевой цикл первого обновления проверяется после публикации 0.1.1.

## Контракт манифеста

| Поле | Правило |
| --- | --- |
| `id` | Всегда `foundry-pf1-ru` |
| `version` | `X.Y.Z`, совпадает с `package.json.version` |
| `manifest` | `https://github.com/laveridu-cell/foundry-pf1-ru/releases/latest/download/module.json` |
| `download` | `https://github.com/laveridu-cell/foundry-pf1-ru/releases/download/vX.Y.Z/foundry-pf1-ru.zip` |
| `compatibility` | `minimum: 13`, `verified: 13`, `maximum: 13` |
| Git-тег | Строго `vX.Y.Z`, указывает на собираемый коммит |

Оба прикреплённых файла содержат один и тот же манифест. ZIP имеет `module.json` в корне и содержит актуальные файлы модуля. Стабильный `manifest` нужен для обнаружения новой версии, закреплённый `download` — для получения её архива. Внутренний манифест старой версии также сохраняет постоянный адрес обновлений.

## Что выполняет автоматика

`validate.yml` на push ветки и PR проверяет JSON/структуру, выполняет тесты Node.js и Python, собирает ZIP и проверяет артефакты. Артефакт `foundry-pf1-ru-review` содержит `module.json` и `foundry-pf1-ru.zip`; GitHub Release не создаётся.

`release.yml` запускается на push **существующего** тега `v*` либо через **Actions → Подготовка черновика релиза → Run workflow** с именем существующего тега. При ручном запуске checkout берёт именно `refs/tags/<tag>`, а не одноимённую ветку. Далее workflow:

1. Проверяет версию, тег, ID, совместимость и адрес архива; сравнивает HEAD с коммитом тега.
2. Проверяет исходные файлы и выполняет все тесты.
3. Собирает `dist/module.json` и `dist/foundry-pf1-ru.zip`.
4. Проверяет совпадение отдельного/архивного манифестов и файлов ZIP с исходниками; сохраняет артефакт запуска.
5. Создаёт **только draft Release** с этими двумя assets и заметками об изменениях.

Используется встроенный `GITHUB_TOKEN` с `contents: write`; личный токен не нужен. Токен не попадает в модуль. В workflow нет шага публикации. Явное подтверждение владельца — отдельная кнопка **Publish release** в GitHub. Если релиз с таким тегом уже существует, команда создания завершается ошибкой и не перезаписывает его assets. При частично созданном черновике сначала осмотрите его и ошибку; опубликованный релиз не пересобирайте поверх старого тега.

## Выпуск 0.1.1 после проверки PR

Ниже инструкция для владельца **после проверки и слияния PR подготовки 0.1.1**. Эти команды при подготовке не выполняются. Повторный `bump` для 0.1.1 не нужен.

1. Проверьте зелёные проверки PR и объедините его с `main`. Убедитесь, что в актуальной `main` оба JSON содержат `0.1.1`, а `module.json.download` указывает на `.../releases/download/v0.1.1/foundry-pf1-ru.zip`. `manifest` должен оставаться постоянным. Просмотрите артефакт CI `foundry-pf1-ru-review`.
2. После решения о выпуске создайте аннотированный тег на проверенном актуальном коммите `main`:

   ```sh
   git switch main
   git pull --ff-only origin main
   git tag -a v0.1.1 -m "PF1 — Русификатор 0.1.1"
   git push origin v0.1.1
   ```

3. Дождитесь успешного **Actions → Подготовка черновика релиза** для `v0.1.1`. Workflow проверяет тег/версию, запускает тесты и сборку, затем создаёт только черновик с `module.json` и `foundry-pf1-ru.zip`. При успешном запуске повторно workflow не запускайте.
4. Откройте Draft `v0.1.1`. Вставьте подготовленные [русские примечания](release-notes/0.1.1.md) в описание вместо автоматически сгенерированного списка PR. Убедитесь, что оба assets присутствуют, версия отдельного и архивного манифестов — `0.1.1`, а в ZIP нет внешней папки над `module.json`. Сам workflow остаётся прежним и создаёт заметки через `--generate-notes`; подготовленный текст применяется владельцем при проверке черновика.
5. После окончательной проверки оставьте **This is a pre-release** выключенным, выберите **Set as latest release** и нажмите **Publish release**. Только опубликованная стабильная 0.1.1 должна стать Latest. Черновик не переключает постоянный манифест.
6. Без входа в GitHub откройте [постоянный манифест](https://github.com/laveridu-cell/foundry-pf1-ru/releases/latest/download/module.json): `version` должна стать `0.1.1`, `download` — [архивом 0.1.1](https://github.com/laveridu-cell/foundry-pf1-ru/releases/download/v0.1.1/foundry-pf1-ru.zip). Скачайте его, сравните манифесты и проверьте переводы, затем выполните сценарий Foundry ниже.

## Проверка обновления 0.1.0 → 0.1.1 в Foundry

1. Начните с установленной **опубликованной 0.1.0** в тестовой установке Foundry 13 / PF1 11.11. Если в папку 0.1.0 вручную копировались файлы PR №4, эти переводы уже могут отображаться: для доказательства доставки используйте чистый [ZIP релиза 0.1.0](https://github.com/laveridu-cell/foundry-pf1-ru/releases/download/v0.1.0/foundry-pf1-ru.zip). Сохраните резервную копию модуля вне `Data/modules` и закройте мир до Setup.
2. Убедитесь, что модуль не заблокирован замком от обновлений и его `manifest` указывает на постоянный URL. После публикации 0.1.1 откройте **Setup → Add-on Modules → Check for Updates**, затем **Update** у **PF1 — Русификатор**. Должна предлагаться **0.1.1**.
3. Проверьте установленный `Data/modules/foundry-pf1-ru/module.json`: ID прежний, версия `0.1.1`, постоянный `manifest` сохранён, `download` содержит `v0.1.1`. В Network/логах загрузки должен использоваться архив этого выпуска.
4. Откройте мир с `ru-ru`, Babele 2.9.1 и libWrapper, выберите русский язык и полностью перезагрузите страницы GM и игрока. Проверьте загрузку трёх JSON без 404, десять подписей выбора листов, «Пункты навыков», «Пункты фоновых навыков» и кнопку «Сохранить». R-01, R-02 и R-03 должны сохранить базовые варианты Phenomen. Проверку фоновых навыков проводите в тестовом мире, модуль сам настройки не переключает.
5. После повторной проверки обновлений 0.1.1 не должна предлагаться как новая версия снова. При проблеме восстановите старую папку/ZIP и заблокируйте модуль до исправления по [инструкции отката](../README.md#откат-при-неудачном-обновлении).

До публикации этот сетевой сценарий считается **не выполненным**. При подготовке проверяются данные обновления: опубликованная 0.1.0 и новая 0.1.1 используют один ID и постоянный `manifest`, новая версия больше старой, а URL ZIP закреплён на `v0.1.1`. Это обеспечивает обнаружение после переключения Latest, но не заменяет реальный прогон менеджера Foundry.

## Первый выпуск 0.1.0: историческая инструкция

Все действия с видимостью, слиянием, тегом и публикацией ниже выполняются **только после отдельного согласования**. Для 0.1.0 команду `bump` запускать не нужно.

1. В GitHub проверьте PR №1 и успешные checks. После разрешения на слияние объедините PR в `main`. Убедитесь, что версия в `main` — **0.1.0** и `download` содержит **`v0.1.0`**.
2. После решения о публичном распространении откройте **Settings → General → Danger Zone → Change repository visibility → Public**. Только владелец меняет этот параметр; публичными станут также исходники и история. Для приватного репозитория нет отдельного публичного канала Releases без авторизации.
3. В **Settings → Actions → General** убедитесь, что GitHub Actions разрешены и политика репозитория допускает требуемое workflow право `contents: write` для встроенного токена.
4. Создайте и отправьте тег на проверенном коммите `main`. Надёжный способ через локальный Git:

   ```sh
   git switch main
   git pull --ff-only origin main
   git tag -a v0.1.0 -m "PF1 — Русификатор 0.1.0"
   git push origin v0.1.0
   ```

   Эти команды являются инструкцией владельцу и не выполнялись при подготовке. Push тега автоматически запускает workflow создания черновика. В GitHub Actions он должен быть доступен после включения workflow в `main`; вручную запускать его повторно при уже успешном запуске не нужно.
5. В **Actions → Подготовка черновика релиза** откройте запуск для `v0.1.0`. Дождитесь зелёного результата; проверьте тег, коммит, результаты тестов и артефакт.
6. В **Releases** откройте созданный **Draft v0.1.0**. Убедитесь, что прикреплены **`module.json`** и **`foundry-pf1-ru.zip`**, в обоих манифестах версия **0.1.0**, внутри ZIP нет лишней внешней папки, а `download` ведёт на `.../download/v0.1.0/foundry-pf1-ru.zip`. Автоматический архив GitHub **Source code** не является дистрибутивом модуля.
7. После окончательного подтверждения публикации снимите **This is a pre-release**, выберите **Set as latest release** и нажмите **Publish release**. Draft и pre-release не используются как стабильный канал обновлений.
8. В окне без входа в GitHub проверьте постоянный [манифест](https://github.com/laveridu-cell/foundry-pf1-ru/releases/latest/download/module.json) и его `download`. Затем установите модуль через Manifest URL в Foundry и проверьте версию, зависимости и перевод. До этого момента полная установка через Releases считается непроверенной.

Если тег существует, а workflow не запускался, после проверки коммита можно выбрать **Run workflow**, ветку workflow `main` и параметр `tag: v0.1.0`. Это не создаёт новый тег. Workflow должен находиться в основной ветке для отображения ручного запуска.

## Следующая версия

Из подготовленной 0.1.1 в следующей рабочей ветке выполните `npm run bump -- patch` (0.1.1 → 0.1.2) или задайте точную следующую версию. Команда меняет только метаданные двух файлов: `module.json` (`version`, `download`) и `package.json` (`version`). Предварительный просмотр: `npm run bump -- patch --dry-run`. Версия только увеличивается; ID, зависимости, постоянный `manifest` и совместимость остаются прежними.

Проведите `npm run check`, `npm test`, `npm run build`, `npm run check:release -- --tag v0.1.2` и ручной прогон; затем подготовьте коммит/PR. Создание тега и публикация снова требуют отдельного решения. Не переносите опубликованные теги и не заменяйте файлы уже выпущенной версии.

Полный сценарий проверки повышения версии выполняется на следующем **реальном согласованном** релизе: установленная 0.1.0 должна получить предложение 0.1.1 в менеджере Foundry, скачать архив `v0.1.1` и сохранить ID. Для этой проверки тестовые публичные Releases не создаются. Локальные тесты уже моделируют изменение версии и проверяют артефакты на временных копиях без сетевой публикации.

Инструкции пользователя по установке, обновлению и откату находятся в [README](../README.md#установка-через-foundry-по-ссылке). При откате восстановите старую папку из копии/предыдущего ZIP и заблокируйте обновления модуля до исправленного выпуска; сам Foundry автоматически версию не понижает.
